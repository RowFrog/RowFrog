# 0067. The app runs on Python 3.14.10

- Date: 2026-11-28
- Status: decided (owner, thread "Keep software versions the same everywhere": card "Yes: uv now, Python after", 27 Nov 2026; the Pi project agreed to the order in the shared versions doc). Follows [0058](0058-app-python-3-14-8.md).
- Where: `.python-version`; used by GitHub (setup-python, and uv on the Mac runners), the Pi (pi-fleet and `run-publish.sh`, uv) and the Mac (update.sh, uv).

## Why

3.14.8 was the highest 3.14 patch that MacPorts' uv 0.13.4 offered. Since #656 (28 Nov 2026) every system has uv 0.13.10, which offers 3.14.10:

- `scripts/check_pins_available.py` (28 Nov 2026): Python 3.14.10 ok in uv's downloads for Linux x86_64, Linux aarch64 and macOS arm64, and in GitHub's setup-python manifest.
- The Pi runs uv 0.13.10 since the 11:30 CET run on 28 Nov ("VERSIONS: same as pinned"), as the Pi project asked before this step.
- All packages in `backend/uv.lock` have cp314 wheels for the three platforms, as for 3.14.8.
- The backend tests pass on 3.14.10 with the locked packages (428 passed, 1 skipped).

## Decision

- `.python-version` is 3.14.10. As in 0058, `requires-python` stays `>=3.12` and ruff's target stays py312, because the Pi runs `source_status.py` and its issue job on Debian's own Python 3.13.
- The next Python patch or minor comes the same way: first the uv that offers it on all three systems, then the Python pin in its own PR.

## Turned down

- 3.15.2: uv 0.13.10 offers it everywhere now, but a minor step goes through its own review (packages, the Pi's scripts), not with a patch step.
- Staying on 3.14.8.
